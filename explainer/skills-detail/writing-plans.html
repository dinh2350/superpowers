2Một plan chứa những gì

Plan là tập hợp các quyết định mà người thực thi không thể tự đưa ra: file nào, tên và chữ ký gì, giá trị nào từ spec, test nào chứng minh từng task.

Header bắt buộc

Mọi plan phải mở đầu bằng khối này

Plan Document Header

Bắt buộc

Làm gìPlan mở đầu bằng tiêu đề # [Tên tính năng] Implementation Plan, một dòng nhắc agent thực thi dùng subagent-driven-development (khuyên dùng) hoặc executing-plans, rồi các mục sau:

MụcNội dung
GoalMột câu: plan này xây cái gì.
Architecture2–3 câu về hướng tiếp cận.
Tech StackCông nghệ và thư viện chính.
SpecĐường dẫn tới spec/design doc mà plan thực thi. Plan lập luận từ spec nên spec đi kèm plan, người thực thi đọc cả hai.
Global ConstraintsYêu cầu toàn dự án lấy từ spec (version tối thiểu, giới hạn dependency, quy tắc đặt tên và copy, nền tảng). Mỗi dòng một yêu cầu, giá trị chép nguyên văn từ spec. Mọi task đều ngầm gồm mục này.
Test StrategyMỗi scenario trong spec (theo lời bạn) một dòng, ghi tên test ở cả unit, integration, e2e và task sở hữu. Dưới bảng là bốn dòng đúng khuôn: Unit run, Integration run, E2E run (mỗi dòng một lệnh) và E2E evidence (đường dẫn). Level không áp dụng thì viết none — <lý do> thay cho lệnh. Script verify-levels đọc đúng bốn dòng này.
Quality GatesNăm dòng đúng khuôn, mỗi dòng một lệnh chạy trên toàn project: Format run (Prettier), Lint run (ESLint), Typecheck run (TypeScript), Build run, Sonar run (SonarQube quality gate). Gate không áp dụng thì viết none — <lý do>. verify-levels đọc cả năm dòng này.
Review FocusNăm input hoặc kiểu lỗi mà spec ngụ ý nhưng test của mọi task chưa phủ, dễ gây hại nhất cho người dùng. Mỗi dòng nêu input hoặc điều kiện và hành vi một người bình thường mong đợi. Sau đó thêm test tương ứng vào task sở hữu đoạn code đó.

Cấu trúc một task

Khuôn cho mọi task trong plan

Task N: [Tên thành phần]

Làm gìMỗi task gồm khối Files, khối Interfaces, rồi các step có checkbox - [ ] để theo dõi.

KhốiNội dung
FilesCreate: đường dẫn file mới · Modify: file cũ kèm dòng (ví dụ existing.py:123-145) · Test: file test.
InterfacesConsumes: task này dùng gì từ task trước, chữ ký chính xác · Produces: task sau dựa vào gì, gồm tên hàm, kiểu tham số và kiểu trả về. Người thực thi chỉ thấy task của mình, nên khối này là cách duy nhất để họ biết tên và kiểu mà task lân cận dùng.

Năm step mẫuMỗi step là một hành động có kết quả kiểm được:

  • Step 1: viết test sẽ fail (đưa code test).
  • Step 2: chạy test, xác nhận nó fail (lệnh và dòng Expected: FAIL …).
  • Step 3: cài hàm với chữ ký chính xác, ở file chính xác. Thêm một dòng về cách làm nếu chữ ký và test còn để ngỏ lựa chọn.
  • Step 4: chạy test, xác nhận pass (Expected: PASS).
  • Step 5: commit (lệnh git add và git commit).

Ba loại test trong plan

Mọi plan phủ đủ cả ba, bỏ level nào phải ghi lý do

Unit, integration, e2e

Nâng cấp
LevelPlan ghi gìAi chạy
UnitMỗi task có unit test cho từng hành vi mới (chính là Step 1–4 ở trên).test-driven-development, trong vòng task
IntegrationTask nào có ranh giới (module với module, DB, mạng, filesystem) thì thêm integration test cạnh đó: cùng các step viết → chạy thấy fail → cài → chạy thấy pass, dùng component thật ở cả hai phía, có Run: và Expected: riêng. Dòng của scenario trong Test Strategy gọi tên nó.test-driven-development, cùng vòng với unit
E2ETask cuối luôn là Task N: End-to-end scenarios, không có code production. Viết mỗi scenario theo lời của spec (không theo code), chạy (Expected: PASS), rồi phá thử hành vi nó kiểm và chạy lại (Expected: FAIL) để chứng minh nó biết fail, khôi phục, commit.verification-before-completion, kèm evidence

Vì sao phải phá thử? E2E viết sau khi code xong thì pass ngay, mà test pass ngay chẳng chứng minh được gì. Bước “thấy nó fail” là cách duy nhất để biết e2e đó thật sự kiểm đúng thứ cần kiểm.

Năm gate chất lượng

Nâng cấp
GateLệnh mặc định (JS/TS)Fail khi
Formatnpx prettier --check .có file chưa được format
Lintnpx eslint . --max-warnings 0có lỗi hoặc cảnh báo
Typechecknpx tsc --noEmitcó lỗi type
Buildnpm run buildproduction build exit khác 0
Sonarnpx sonar-scanner -Dsonar.qualitygate.wait=truequality gate fail: bug, vulnerability, code smell, coverage
  • Đọc project trước khi điền: script trong package.json, config Prettier/ESLint/tsconfig, sonar-project.properties, CI. Ghi đúng thứ CI chạy; script riêng của project được ưu tiên hơn lệnh mặc định.
  • Stack khác dùng lệnh tương đương (ruff format --check, go vet ./..., cargo clippy -- -D warnings) hoặc none — <lý do>.
  • Chỉ bỏ gate khi nó thật sự không áp dụng (không có TypeScript, không có bước build). “Chưa cài” trong project JS/TS là một lỗ hổng, không phải lý do: task đầu của plan cài tool đó, để bạn thấy nó khi duyệt plan. Sonar là ngoại lệ vì cần server mà plan không tạo được: hỏi bạn xem repo có Sonar project không, và chỉ ghi none khi bạn đồng ý.
  • Sonar đọc coverage: điều kiện coverage của quality gate đọc báo cáo mà test ghi ra, nên lệnh Unit run phải ghi nó đúng nơi scanner tìm (mặc định coverage/lcov.info).
  • Token Sonar không bao giờ nằm trong plan (plan được commit). Scanner đọc SONAR_TOKEN từ môi trường, và verify-levels từ chối plan nào ghi token ra.

3Viết sao cho đúng cỡ

Plan quá thiếu thì người thực thi phải đoán. Plan quá thừa thì thành bản chép của chương trình. Phần này nói cách tìm điểm giữa.

Kiểm tra phạm vi

Làm gìNếu spec bao nhiều hệ con độc lập, lẽ ra nó đã được tách thành các spec con ở bước brainstorming. Chưa tách thì đề xuất tách thành các plan riêng, mỗi hệ con một plan. Mỗi plan phải tự tạo ra phần mềm chạy và test được.

Dùng khiĐầu tiên, trước khi vạch cấu trúc file.

Vạch cấu trúc file

Làm gìTrước khi chia task, liệt kê file sẽ tạo hoặc sửa và trách nhiệm của từng file. Đây là nơi chốt các quyết định phân rã.

  • Mỗi file một trách nhiệm rõ, giao diện rõ.
  • Ưu tiên file nhỏ, tập trung: agent giữ được trọn file trong context và sửa đáng tin hơn.
  • Thứ thay đổi cùng nhau thì để cùng nhau. Chia theo trách nhiệm, không theo tầng kỹ thuật.
  • Codebase có sẵn: theo pattern hiện tại. Nếu file đang sửa đã quá lớn thì được đưa việc tách file vào plan.

Cỡ một task

Làm gìTask là đơn vị nhỏ nhất mà có chu trình test riêng và đáng để một reviewer mới chặn lại. Gộp setup, cấu hình, scaffolding và tài liệu vào task cần chúng. Chỉ tách khi reviewer có thể hợp lý từ chối task này mà vẫn duyệt task bên cạnh.

Step xong khi người thực thi viết được đúng một thứ hợp lý từ nó. Không cần đầy đủ, cần không mơ hồ
Loại stepMang theo (và không hơn)
Step testTên test và các assert bằng code, với giá trị chính xác của spec.
Step codeChữ ký chính xác (tên, tham số, kiểu trả về), file chứa nó, và các giá trị cụ thể spec ấn định. Người thực thi tự viết phần thân. Chỉ đưa thân hàm khi đó là thuật toán mà chữ ký và test không xác định, hoặc là copy cố định theo spec.

4Tự review và bàn giao

Plan viết xong thì tự đối chiếu với spec bằng con mắt mới. Đây là checklist agent tự chạy, không phải dispatch subagent.

Self-review: 7 kiểm tra

#Kiểm traCâu hỏi
1Spec coverageMỗi mục hay yêu cầu trong spec có task thực hiện không? Liệt kê chỗ thiếu.
2Step scanMỗi step cho phép viết đúng một thứ hợp lý và không mang nhiều hơn thế? Dòng không quyết định gì là thiếu. Thân hàm mà chữ ký và test đã xác định là chép lại. Sửa cả hai.
3Type consistencyTên hàm, chữ ký, tên thuộc tính ở task sau có khớp task trước không? (clearLayers() ở Task 3 mà thành clearFullLayers() ở Task 7 là lỗi.)
4Review FocusMỗi input hay kiểu lỗi mà spec ngụ ý có task nào có test phủ không? Năm cái chưa phủ mà dễ gây hại nhất vào mục Review Focus, mỗi dòng thêm test vào task sở hữu. Mục rỗng nghĩa là đã kiểm và không thấy, không phải bỏ qua.
5ProportionSo độ dài plan với spec. Plan dài gấp nhiều lần spec là bản chép chương trình. Nếu code block là phần lớn tài liệu, thay thân hàm bằng chữ ký, tên test và assert.
6Test levelsMỗi dòng Test Strategy có tên test ở unit, integration và e2e, hoặc một dòng giải thích vì sao level đó không áp dụng? Mỗi integration test nằm đúng task đi qua ranh giới nó kiểm? Task cuối có phải task e2e? Ba dòng Unit run, Integration run, E2E run đều có lệnh hoặc none — <lý do>, và dòng E2E evidence có đường dẫn? Lệnh E2E, chạy đúng như đã viết, có ghi evidence vào đường dẫn đó không (kể cả biến môi trường nó cần, đặt ngay trên dòng lệnh)? Lệnh chỉ ghi evidence khi một biến được đặt mà không ai đặt nó thì exit 0 nhưng không có evidence, và sẽ fail ở bước verify.
7Quality gatesMỗi dòng trong năm dòng Quality Gates có một lệnh toàn project hoặc none — <lý do>, và lý do có còn đúng với file config và CI của project không? Nếu dòng Sonar là lệnh, Unit run có ghi báo cáo coverage mà nó đọc không, và có dòng nào ghi sẵn token không?

Thấy lỗi thì sửa ngay tại chỗ, không cần review lại. Thấy yêu cầu của spec chưa có task thì thêm task.

Bàn giao: bạn duyệt và chọn cách chạy

Làm gìLưu plan rồi gửi link cho bạn đọc. Nếu bạn đã nói rõ cách thực thi từ trước, agent chỉ xin bạn duyệt và xác nhận plan đúng ý, chờ duyệt xong mới làm, rồi dùng đúng cách bạn đã chọn. Nếu chưa, agent hỏi bạn duyệt plan và chọn một trong hai:

Cách chạyMô tảSkill sẽ gọi
Subagent-drivenMỗi task một subagent mới, và một reviewer mới kiểm trước khi sang task kế, cuối cùng review cả nhánh. Kỹ nhất, nhưng tốn một context mới cho mỗi task và mỗi review.subagent-driven-development
NativeAgent tự làm mọi task trong phiên này, rồi một reviewer mới trên model mạnh nhất kiểm cả nhánh. Rẻ và nhanh nhất, nhưng chưa có review độc lập tới cuối. Chạy tốt cả với model tầm trung vì plan đã mang sẵn thiết kế.executing-plans

Agent phải nêu khuyến nghị của mình cho plan này, kèm một câu lý do rút từ chính plan: các task phụ thuộc vào interface của nhau tới đâu, có bao nhiêu task, và nếu lỗi lọt qua thì tốn kém ra sao.
