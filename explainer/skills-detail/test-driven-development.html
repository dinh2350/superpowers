test-driven-development

Viết test trước. Xem nó fail. Viết code tối thiểu cho nó pass. Nếu chưa từng thấy test fail thì không biết được nó có kiểm đúng thứ cần kiểm hay không.

2Luật sắt

“Vi phạm câu chữ của quy tắc là vi phạm tinh thần của nó.” Nghĩ “lần này bỏ TDD thôi”? Dừng lại, đó là biện hộ.

NO PRODUCTION CODE WITHOUT A FAILING TEST FIRSTViết code trước test? Xóa nó, làm lại. Không giữ làm “tham khảo”, không “chỉnh” nó khi viết test, không nhìn nó. Xóa nghĩa là xóa. Cài lại từ test.

Khi nào dùng

Làm gìLuôn luôn: tính năng mới, sửa bug, refactor, đổi hành vi.

Ngoại lệ (phải hỏi bạn)Prototype bỏ đi · code sinh tự động · file cấu hình.

3Chu trình Red–Green–Refactor

Năm bước. Hai bước “verify” là bắt buộc, không bao giờ bỏ.

1

RED: viết test sẽ fail

Làm gìViết một test tối thiểu cho thấy điều cần xảy ra. Một hành vi, tên rõ, dùng code thật (không mock trừ khi bất khả kháng).

Tốt: tên rõ, kiểm hành vi thật, một việc

test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});

Dở: tên mơ hồ, kiểm mock chứ không kiểm code

test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});

Kết quảLàm gì

Test errorSửa lỗi, chạy lại tới khi nó fail đúng cách.

3

GREEN: code tối thiểu

Làm gìViết code đơn giản nhất cho test pass. Không thêm tính năng, không refactor code khác, không “cải thiện” quá phạm vi của test.

Tốt: vừa đủ để pass

async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}

Dở: làm quá tay (YAGNI)

async function retryOperation<T>(
  fn: () => Promise<T>,
  options?: {
    maxRetries?: number;
    backoff?: 'linear' | 'exponential';
    onRetry?: (attempt: number) => void;
  }
): Promise<T> {
  // YAGNI
}

Verify GREEN: xem nó pass

Bắt buộc
npm test path/to/test.test.ts

Làm gìXác nhận: test pass, các test khác vẫn pass, output sạch (không lỗi, không warning).

Kết quảLàm gì
Test failSửa code, không sửa test.
Test khác failSửa ngay.

“Các test khác” là suite của dự ánTest vừa viết xanh chưa phải suite xanh. Trước khi gọi là xong, chạy lệnh test của dự án (pytest trần, npm test, cargo test, tùy repo) ngay cả khi task chỉ nêu một file test. Phạm vi của task giới hạn sản phẩm bàn giao, không giới hạn việc kiểm chứng. Mọi lỗi lần chạy đó cho thấy, kể cả lỗi agent không gây ra, đều phải có tên trong báo cáo: một test đỏ đã thấy trôi qua mà không nhắc là báo cáo bị làm sai bằng cách bỏ sót.

Ba mức test

Chu trình giống nhau ở mọi mức. Khác nhau ở lượng code thật đứng sau test và lúc nó chạy

Test Levels: unit, integration, e2e

Nâng cấp
MứcChứng minhTrong vòng task?
UnitMột hành vi của một đơn vị. Chỉ phần chậm hoặc bên ngoài mới bị làm giả.Có, mọi hành vi mới
IntegrationCác component thật chạy cùng nhau qua một ranh giới: module với module, DB, mạng, filesystem.Có, khi task của plan gọi tên nó hoặc sản phẩm của task đi qua ranh giới
End-to-endKịch bản của một người dùng qua hệ thống đang chạy.Không. Task cuối của plan viết nó, verification-before-completion chạy nó

IntegrationRED, verify RED, GREEN, verify GREEN, y như unit test: Luật sắt áp dụng nguyên vẹn. Dùng component thật ở cả hai phía của đường nối. Mock phía bên kia thì nó thành unit test. Task đã gọi tên một integration test thì viết nó trước và xem nó fail. Task đi qua ranh giới mà plan không nêu test nào thì plan có lỗ hổng: vẫn viết test, và nói rõ trong báo cáo.

End-to-endKhông nằm trong chu trình này: nó cần cả hệ thống và quá chậm để chạy từng step. Không được báo một tính năng là xong khi chưa có nó. Cổng đó thuộc verification-before-completion.

4Test tốt và ví dụ sửa bug

Test tốt tối thiểu, rõ, và cho thấy API mong muốn. Khi viết hay đổi bất kỳ test nào, skill còn một file riêng về cách giữ test trung thực.

Tiêu chíTốtDở
Tối thiểuMột việc. Có “và” trong tên? Tách ra.test('validates email and domain and whitespace')
RõTên mô tả hành vitest('test1')
Thể hiện ý đồCho thấy API mong muốnChe khuất việc code phải làm

writing-good-tests.md

Làm gìBốn quy tắc giữ test trung thực:

  • Nêu thay đổi production nào sẽ làm test fail, trước khi viết nó.
  • Assert trên hành vi thật, không bao giờ trên hành vi của mock.
  • Giữ code chỉ-để-test trong tiện ích test, ngoài class production.
  • Hiểu tác dụng phụ của một dependency trước khi mock nó.

function submitForm(data: FormData) {

    return { error: 'Email required' };
  }

Verify GREEN

PASS

REFACTORTách phần validate ra nếu có nhiều trường.

Tìm ra bug? Viết test fail tái hiện nó, rồi đi theo chu trình. Test vừa chứng minh bản sửa vừa chặn tái phát. Không bao giờ sửa bug mà không có test.

5Checklist, Red Flags và bào chữa

Không tick hết được checklist nghĩa là bạn đã bỏ TDD. Gặp bất kỳ red flag nào: xóa code, làm lại từ đầu bằng TDD.

Checklist trước khi báo xong

  • Mỗi hàm/phương thức mới đều có test.
  • Mọi ranh giới mà thay đổi đi qua đều có integration test, dùng component thật ở hai phía.
  • Đã thấy từng test fail trước khi cài.
  • Mỗi test fail vì đúng lý do (thiếu tính năng, không phải gõ sai).
  • Đã viết code tối thiểu cho mỗi test pass.
  • Mọi test pass.
  • Output sạch (không lỗi, không warning).
  • Test dùng code thật (chỉ mock khi bất khả kháng).
  • Đã phủ các ca biên và ca lỗi.
↑ Về diagram

Red Flags: dừng lại, làm lại từ đầu

  • Code trước test.
  • Test viết sau khi cài.
  • Test pass ngay lập tức.
  • Không giải thích được vì sao test fail.
  • Test được thêm “sau”.
  • Tự nhủ “chỉ lần này thôi”.
  • “Tôi đã test tay rồi.”
  • “Test sau cũng đạt cùng mục đích.”
  • “Quan trọng là tinh thần, không phải nghi thức.”
  • “Giữ làm tham khảo” hoặc “chỉnh code có sẵn”.
  • “Đã tốn X giờ, xóa đi thì phí.”
  • “TDD giáo điều, tôi đang thực dụng.”
  • “Cái này khác vì…”

Những lời bào chữa hay gặp

Bảng Common Rationalizations của skill
Agent tự nhủThực tế
“Quá đơn giản để test”Code đơn giản vẫn hỏng. Viết test mất 30 giây.
“Tôi test sau”Test viết sau pass ngay, nên chẳng chứng minh được gì. Chúng có thể kiểm sai thứ, kiểm cách cài thay vì hành vi, hoặc bỏ sót ca biên bạn quên. Chưa từng thấy nó fail nên chưa chứng minh được nó bắt được bug. Test trước ép phải có lần fail đó.
“Test sau cũng đạt cùng mục đích (tinh thần, không phải nghi thức)”Test sau trả lời “code này làm gì?”; test trước trả lời “code này NÊN làm gì?”. Test viết sau bị thiên lệch bởi code đã viết: chỉ kiểm những ca đã nhớ, không phải những ca lẽ ra sẽ khám phá. Có độ phủ mà không có bằng chứng test hoạt động.
“Đã test tay rồi”Test tay là ad hoc: không có bản ghi đã phủ gì, không chạy lại được khi code đổi, dễ quên ca dưới áp lực. “Tôi thử thì chạy” không phải toàn diện. Test tự động chạy giống hệt nhau mỗi lần.
“Xóa X giờ làm việc thì phí”Chi phí chìm: thời gian đó mất rồi dù thế nào. Lựa chọn thật là viết lại bằng TDD (tin cậy cao) hay giữ code rồi gắn test sau (tin cậy thấp, nhiều bug). Giữ code không tin cậy được mới là phí.
“Giữ làm tham khảo, viết test trước”Rồi sẽ chỉnh nó. Đó là test sau. Xóa nghĩa là xóa.
“Cần khám phá trước”Được. Bỏ đi phần khám phá, bắt đầu bằng TDD.
“Test khó nghĩa là thiết kế chưa rõ”Hãy nghe test. Khó test nghĩa là khó dùng.
“TDD làm tôi chậm”TDD chính là con đường thực dụng: bắt bug trước khi commit, ngăn regression, cho phép refactor không sợ. Lối tắt “thực dụng” nghĩa là debug trên production, chậm hơn.
“Test tay nhanh hơn”Test tay không chứng minh được ca biên. Sẽ phải test lại mỗi lần đổi.
“Code có sẵn chưa có test”Đang cải thiện nó nghĩa là thêm test cho code đang có.
“Unit test phủ rồi, integration là thừa”Unit pass trong khi chỗ nối giữa chúng vỡ: sai tên trường, sai thứ tự, sai định dạng. Một đường nối bị mock chỉ kiểm cái bạn đoán về phía bên kia.
