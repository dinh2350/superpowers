3 · Ba loại test, có cổng kiểm

Nâng cấp

Vấn đềUnit xanh nhưng chưa ai thử kịch bản thật. Agent nói “xong” khi e2e chưa chạy, hoặc chạy mà không để lại bằng chứng.

  • writing-plans: mục Test Strategy (mỗi scenario một dòng, test ở cả unit, integration, e2e), bốn dòng lệnh Unit run, Integration run, E2E run, E2E evidence, và task cuối luôn là e2e, phải chứng minh được nó có thể fail.
  • test-driven-development: unit và integration cùng vòng red-green; e2e nằm ngoài vòng.

4 · Gate chất lượng: Prettier, ESLint, tsc, build, Sonar

Nâng cấp

Vấn đềTest xanh nhưng CI đỏ vì chưa format, lint, đúng type, build, hay quality gate. Agent còn dễ làm gate pass bằng cách tắt tiếng thay vì sửa. Và trên repo đã đỏ sẵn ở commit gốc thì không plan nào qua nổi gate toàn project: chỉ còn cách sửa code plan chưa từng đụng tới, hoặc bỏ gate.

  • verify-levels chạy 8 level: thêm format, lint, typecheck, build, sonar vào ba level test. Thứ tự rẻ nhất trước; Sonar cuối vì quality gate đọc coverage do test ghi.
  • writing-plans thêm mục Quality Gates (5 dòng lệnh toàn project) và mục tự kiểm số 7. Gate không áp dụng thì ghi none — <lý do>.
  • Gate fail thì script in cách sửa và những thứ không phải là sửa: eslint-disable, @ts-ignore, NOSONAR, config nới lỏng.
  • Plan ghi sẵn token Sonar bị từ chối; scanner đọc SONAR_TOKEN từ môi trường.
  • none — <lý do> bọc trong backtick vẫn là skip, không bị chạy như một lệnh tên none. Tìm ra khi chạy script với Prettier, ESLint, tsc thật.
  • Reviewer cuối kiểm lý do của gate bị skip và tìm trong diff các kiểu tắt tiếng.
  • Baseline đã đỏ. writing-plans chạy Format, Lint, Typecheck, Unit và Integration một lần trên commit gốc. Level xanh vẫn toàn project; level đỏ thì giới hạn theo file plan đụng tới: Lint theo danh sách file (có chặn danh sách rỗng, vì ESLint 9 không có file thì lint cả thư mục), Typecheck qua changed-only, Unit và Integration chạy các test liên quan tới file đổi, Format chỉ file mới thêm. Sonar không cần giới hạn vì quality gate chỉ xét code mới; Build và E2E luôn toàn project.
  • changed-only BASE -- LỆNH (script mới, 74 dòng): chạy lệnh và pass khi không finding nào nó in ra (path(line,col) hay path:line:col) nằm trong file đã đổi từ BASE. Cần vì tsc không nhận danh sách file (có file thì nó bỏ qua tsconfig). Lệnh chết mà không in finding nào, BASE không phải commit, hay awk lỗi đều là fail, nên tool crash không bao giờ bị đọc là “sạch”. verify-levels đưa nó vào PATH để dòng lệnh trong plan gọi được.
  • Ranh giới là file plan đụng tới. Lỗi lint, type, test trong file plan sửa thì sửa, kể cả lỗi có từ trước. Lỗi ở file khác thì để nguyên và báo cho bạn: trong câu baseline của plan và trong mục lo ngại của báo cáo implementer.

5 · Dùng thư viện theo docs, không theo code bên cạnh

Nâng cấp

Vấn đềPlan và implementer prompt bảo agent “theo pattern có sẵn” trong codebase. Codebase yếu thì pattern yếu bị chép sang code mới. Reviewer thì chỉ phán theo trí nhớ của model, nên chuẩn của người viết và người review không giống nhau, và trí nhớ đó có thể cũ so với version đang dùng.

  • writing-plans và implementer-prompt.md: tên và vị trí file lấy từ code xung quanh, nhưng chất lượng thì không. Cách dùng thư viện hay framework theo docs của đúng version trong lockfile (Context7 nếu có, không thì docs chính thức), không theo cách code bên cạnh làm.
  • Self-review của implementer đổi câu hỏi “đã theo pattern của codebase chưa” thành “đã theo naming và layout của codebase, và docs (không phải code gần đó) cho cách dùng thư viện chưa”.
  • code-reviewer.md thêm mục Library and framework usage: với mỗi thư viện mà diff đụng tới, đối chiếu cách dùng với docs đúng version trong lockfile, dẫn trang docs cho mỗi phát hiện. Không truy cập được docs thì ghi dưới “Declined to judge”, không đoán.

3Luồng verify-levels: từ không có, tới 3, tới 8 level

Bản gốc không có script nào chạy cổng cấp plan: agent tự chạy test rồi nói “xong”. Giờ có một script chạy tám level theo thứ tự này.

format→ lint→ typecheck→ build→ unit→ integration→ e2e→ sonar

testnhóm 3: ba loại test   gatenhóm 4: năm gate chất lượng

Quy tắc của script

  • Đọc hết plan trước khi chạy gì: plan thiếu dòng hay sai định dạng bị từ chối ngay (exit 2).
  • Dừng ở level fail đầu tiên và trả đúng exit status của lệnh đó. Level sau không chạy.
  • E2E pass chỉ khi lệnh exit 0 và có file evidence mới, không rỗng. Sonar chạy cuối vì cần coverage do test ghi.
  • Thành công thì ghi docs/superpowers/evidence/<plan>/verify.txt gắn với HEAD (git-ignored). --check không chạy gì, chỉ chấp nhận record đủ 8 level cho đúng HEAD và không có file tracked nào đổi sau đó.
  • Level không áp dụng ghi none — <lý do>; lý do được ghi vào record và reviewer cuối kiểm nó còn đúng.
  • changed-only nằm trong PATH khi script chạy, nên một dòng lệnh trong plan gọi được nó (xem nhóm 4).

5Những chỗ cần bạn quyết định

Đây là các lựa chọn thiết kế đã được chọn mặc định. Chỗ nào bạn không đồng ý thì nói, vì mỗi cái đều đổi được.

Tám lựa chọn

  • Năm dòng Quality Gates là bắt buộc. Plan cũ thiếu chúng bị verify-levels từ chối (exit 2) kèm thông báo nêu dòng còn thiếu. Nếu muốn mềm hơn, thiếu dòng có thể mặc định là none, nhưng khi đó gate dễ bị quên.
  • Gate chỉ chạy ở cuối plan, không sau từng task. Lỗi format và lint có thể dồn đến cuối mới lộ. Có thể thêm bước format, lint, typecheck vào implementer prompt nếu bạn muốn bắt sớm.
  • Lối thoát none — <lý do> do reviewer kiểm, không phải script. Script có thể chặn cứng khi thấy tsconfig.json hay sonar-project.properties mà gate là none, đổi lại cần thêm cách bỏ qua hợp lệ.
  • Project JS/TS chưa có Prettier, ESLint hay tsc. Task đầu của plan sẽ cài chúng, tức là thêm dependency vào project của bạn; bạn thấy việc đó khi duyệt plan.
  • Sonar cần server và SONAR_TOKEN. Không có thì chỉ bạn mới được quyết none; agent không tự quyết.
  • Baseline đỏ: chỉ sửa file plan đụng tới. Lỗi ở file khác bị để nguyên và báo cho bạn. Muốn repo sạch hơn thì làm một plan riêng; muốn plan tự dọn thì bỏ ranh giới này, đổi lại diff của plan phình ra với code không liên quan. Test liên quan theo import graph nên không thấy dynamic import.
  • Docs là chuẩn cho cách dùng thư viện, không cho kiến trúc. Tên và vị trí file vẫn theo code xung quanh. Reviewer tra docs thì tốn thêm lượt gọi tool mỗi lần review; không có Context7 hay docs thì nó ghi vào “Declined to judge” chứ không đoán.
  • Chỉ phù hợp fork này. AGENTS.md của repo upstream nói PR theo kiểu fork-specific hoặc phụ thuộc bên thứ ba sẽ bị đóng, nên đừng gửi lên upstream.
